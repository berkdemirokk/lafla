# I18N — Lafla Mobile

Lafla ships Turkish-first, but the UI is already English-ready under the hood. This doc explains the lightweight i18n scaffold in `apps/mobile/lib/i18n.ts` and how to use it without pulling in `i18next` or any other dependency.

## ⚠️ FUTURE — Multi-language expansion (May 2026 note)

Lafla's roadmap includes supporting **other source languages** (Arabic, Spanish, etc. speakers learning English) and possibly **other target languages** (TR speakers learning DE, FR, etc.) in future versions.

**Brand decision:** the app name "Lafla" stays Turkish across all markets.

**Architectural implications for new code (so we don't paint into a corner):**
- Lesson content should NOT hard-code Turkish in field names. Existing `tr_explanation`, `tr_hint`, `tr_translation` patterns are fine for now but consider extracting to `explanation`, `hint`, `translation` keyed by locale when a second source language is added.
- New screens MUST use `t()` from `lib/i18n.ts` — no inline TR strings.
- New content data files (lessons, scenes, drills) can stay TR-first for now; multi-language content will be a parallel translation pass when a second source language is funded.
- Don't assume `tr` is the only source — use `getLocale()` where logic depends on it.
- Coach persona name (`Maya`) is locale-agnostic and can stay.

**Out of scope for current sprint:** actual multi-language content generation. Just don't lock the architecture against it.

## TL;DR

```tsx
import { t, useTranslation } from "@/lib/i18n";

// Anywhere (non-React): static lookup of the current locale.
const label = t("common.continue");

// Inside a component: subscribes to locale changes so the screen re-renders
// when the user switches language in Settings.
function MyScreen() {
  const { t, locale, setLocale } = useTranslation();
  return <Text>{t("feed.title")}</Text>;
}

// With variables — {name}-style placeholders in the JSON value.
t("welcome_user", { name: "Berk" });
```

## What's in the box

| File | Purpose |
| --- | --- |
| `apps/mobile/lib/i18n.ts` | `t()`, `useTranslation()`, `getLocale()`, `setLocale()`, `hydrateLocale()` |
| `apps/mobile/locales/tr.json` | Turkish dictionary (default / fallback locale) |
| `apps/mobile/locales/en.json` | English dictionary |

The dictionaries are flat `Record<string, string>` JSON. Keys use dot notation by convention (`scope.name`), but the scaffold doesn't enforce nesting — it's plain string keys all the way down.

## API

### `t(key, vars?)`

```ts
t(key: string, vars?: Record<string, string>): string
```

Returns the translation for `key` in the current locale. Lookup order:

1. Current locale (`tr` or `en`).
2. Default locale (`tr`).
3. The `key` string itself — handy in dev because missing translations show up verbatim instead of as empty space.

`vars` interpolates `{placeholder}` tokens inside the value. Unknown placeholders are left untouched (also a dev signal).

### `useTranslation()`

```ts
const { t, locale, setLocale } = useTranslation();
```

React hook. Subscribes the component to locale changes, so a `setLocale("en")` call anywhere in the app immediately re-renders all consumers. Use this inside components instead of the bare `t()` import so the screen reacts to language switches.

### `getLocale()` / `setLocale(locale)`

```ts
getLocale(): "tr" | "en"
setLocale(locale: "tr" | "en"): Promise<void>
```

`setLocale` persists to AsyncStorage (`lafla.locale`) and notifies subscribed hooks. Awaitable, but the UI updates synchronously — the await is only for the storage write.

### `hydrateLocale()`

```ts
hydrateLocale(): Promise<void>
```

Loads the persisted locale (or detects from device via `expo-localization` if installed) on app boot. Called automatically when the module loads — you only need to await it if your splash screen needs the right strings before the first paint.

## How to add a new key

1. Pick a dot-namespaced key: `scope.name`. Existing scopes: `common`, `feed`, `profile`, `scenario`.
2. Add it to **both** `locales/tr.json` and `locales/en.json`. Keep keys alphabetised within each scope for easier diffs.
3. Use `t("scope.name")` in your component.

If you ship a key in only one locale, the missing side falls back to TR, then to the raw key string. No crashes, just a visible signal.

### Interpolation

Use `{var}` placeholders inside the JSON value:

```json
{
  "feed.greet_user": "Selam {name}, bugün {count} ders var"
}
```

```ts
t("feed.greet_user", { name: "Berk", count: "3" });
// → "Selam Berk, bugün 3 ders var"
```

All values are strings — coerce numbers at the call site (`String(count)` or template literals).

## Default locale and device detection

- Default: `tr` (matches the Türk-first stance in ADR-003).
- If `expo-localization` is installed, an unseen first-launch device with an English system locale will start in `en`. The module is optional — the scaffold uses a guarded `require()`, so adding it later is a no-op upgrade.
- Once the user explicitly picks a language in Settings, the choice is persisted to AsyncStorage and device detection is ignored on subsequent launches.

## Locale switching plan

The scaffold is opt-in — no existing screens have been migrated. Roll-out plan:

1. **Settings → Language toggle** (next step).
   Add a row to `app/settings.tsx` that calls `setLocale("tr" | "en")`. Two-option segmented control or a simple radio.
2. **Migrate one screen at a time.**
   Start with `app/index.tsx` (feed) or `app/settings.tsx` itself. Replace hardcoded Turkish strings with `t(...)` calls, add missing keys to both JSON files as you go.
3. **Lesson content stays separate.**
   Lesson scripts (`apps/mobile/data/*-lesson.ts`) are *content*, not UI chrome. They remain Turkish prompts → English target lines and do not flow through `t()`. The scaffold is for the app shell.
4. **Cutover criteria.**
   When >80% of UI strings go through `t()` and both JSON files are in sync (same key set), publish the language toggle. Until then, the toggle stays behind a dev flag.

## Why not i18next?

- Bundle size: i18next + react-i18next is ~30 KB gzipped before plugins. Our needs (two locales, flat dictionary, AsyncStorage persistence) are ~150 lines of code.
- Type safety: a flat JSON dictionary lets us add a typed key union later (`keyof typeof trMessages`) without touching call sites.
- One less peer-dependency footgun across Expo SDK upgrades.

If we hit pluralisation, gender, or 5+ locales, revisit. Until then this is enough.

## Constraints honoured

- Did not modify `app.json` or `package.json`.
- No new dependencies installed.
- Existing screens untouched — migration is gradual and opt-in.
